| 面板内容行数 | 同函数中段的表头 3 行、pass 表 5 行、滑杆 4 行 × 2、状态 3 行；行数变了高度会跟着变（高度始终按内容测量，不会裁剪） |
| 滑杆长度与分布 | 同函数：`const float sw = panelW - 2.0f * pad - 96.0f;`（`sw` 是长滑杆宽度，曝光/bloom 三个短滑杆取 `sw * 0.31` 等比例） |
| UI 与字体总体比例 | 运行期按 `U` 循环，或 `--hud-scale <f>` 钉死；自动档位在 `viz/src/viz_main.cpp` 的 `applyAutoScale`（1 / 1.5 / 2 / 3 四档，阈值 `fit >= 1.4 / 1.9 / 2.8`） |
| 左下角操作指南 | `viz/src/hud.cpp`，`help[5]` 数组（改文字即可，底板宽度会自动跟随） |
| 罗盘位置与半径 | `viz/src/hud.cpp` 中 `compass(cx, cy, 52.0f, st)` 的调用点，以及 `Hud::compass` 内部 |

而不是把面板撑宽。高度仍按实际内容测量，日轨演示会多两行。

## 1. bloom 是什么？为什么调高之后会出现意料之外的亮斑？

### 它有什么用：把"超出屏幕能显示范围的亮度"变成看得见的光晕

光追算出的是物理量：接收器光斑峰值 4800 W/px、太阳盘在着色里是 16 倍白点。
而显示器最多只能显示 1.0（纯白）。曝光 + ACES 把这段动态范围压进 0–1 之后，
所有"很亮"的东西都会变成**一样白**——太阳、镜面高光、光斑核心都会糊成同一块纯白，
看起来像贴纸，也看不出"这里到底比其他地方亮多少"。

bloom 做的就是把这个信息补回来：**把画面上过曝的区域摊开成光晕再加回去**，
让观众读到"这里亮到镜头/眼睛都开始散射了"。它模仿的是相机镜头内部的散射与眼睛的眩光，
不是在模拟物理光线传播——所以它是一层**纯屏幕空间**的效果，只在最后合成时生效。

`docs/figs/bloom_effect.png`（`tools/bloom_effect.py` 生成，接收器特写同一帧）：

| 配置 | 变亮的屏幕像素 | 占全屏 | 平均增量 | 最大增量 |
|---|---|---|---|---|
| bloom 关 | 0 | 0% | 0 | 0 |
| **0.55 / thr 2.5（默认）** | 90 625 | **9.83%** | +0.0161 | +0.902 |
| 1.50 / thr 2.5（过头） | 104 355 | 11.32% | +0.0242 | +0.914 |

也就是说：默认档下光斑周围约 10% 的屏幕被"提亮"了一层很薄的光（平均只有 0.016），
而光斑核心本身被推到接近过曝（+0.902）——这正是"强光源"的观感。
强度拉到 1.5 时扩散面积和整体亮度都再上一个台阶，光斑细节开始被自己的光晕盖住。

### "哪些像素被允许发光"——是的，就是屏幕像素

亮通道的输入是**已经渲染完成的 HDR 画面**（每个屏幕像素一个线性 RGB 值），
它按数值判断这个像素够不够亮，不关心它是太阳、镜面还是天空。
所以阈值是唯一把"**光源**"和"**只是比较亮的表面**"区分开的东西：

- 天空、地面、镜面本身都在 1.0 附近或以下 → 它们只是"表面"；
- 太阳盘 16×、镜面高光 8×、接收器光斑核心 3.6× → 这些才是"亮到显示不出来"的地方。

阈值定在 1.0 时，天空自己越过了门槛，于是**整片天空被当成光源**摊开成光晕
（实测 19.53% 的画面被点亮，见 `docs/figs/bloom_sources.png`）——这就是"意料之外的亮斑"。

### 为什么不干脆让所有像素都参与

如果去掉阈值、让整幅画面按亮度加权模糊再加回来，等价于给图像叠一层随位置变化的白雾：

- 对比度整体下降，画面发灰；
- 任何"暗物体压在亮背景上"的边缘（塔、螺栓、镜框）都会拖出一圈光晕，因为它们附近
  本来就有亮像素，而模糊不知道该不该散；
- "亮度感"反而被破坏：当所有东西都在发光时，就没有东西显得更亮。

所以工业上普遍采用"阈值 + 软膝"：阈值决定分界线，软膝（代码里 `knee = 0.35`）
让分界线附近平滑过渡，避免硬切边导致光斑边缘"跳变"。

### 在这个项目里的具体作用

1. **让光斑读起来是个强光源**：优化后面型把能量聚到很小的面积上（S95 46.26 m²、峰值 4808 W/px），
   光晕是唯一能在 8-bit 显示器上表达"这么亮"的手段；
2. **但不能盖住数据**：光斑图的对数映射、S95 等值线、峰值读数才是要展示的信息，
   所以阈值取 2.5、强度取 0.55——光晕只包在发射核心外面（平均增量 0.016），不糊掉结构；
3. **不影响测量**：HUD 面板与右下角光斑图是**合成之后**画的，永远不会被 bloom 影响；
4. **成本与参数无关**：9 个 pass 合计约 0.078 ms，改阈值/强度不改变开销。

### 管线位置：bloom 发生在 tonemap 之前

```
compute 链（flux）→ scene pass → HDR 目标（R16G16B16A16_SFLOAT，线性、未 tonemap）
                                   │
                                   ├─ 亮通道      fsBloomPre   → mip0   （半分辨率起）
                                   ├─ 降采样 ×4   fsBloomDown  → mip1..mip4（1/4 … 1/32）
                                   ├─ 升采样 ×4   fsBloomUp    → 加法混合回上一级
                                   └─ 合成        fsComposite
                                         col = hdr + bloom * bloomStrength    ← 强度只在这里
                                         col *= exposure ; ACES ; vignette → sRGB
```

| 参数 | 出现位置 | 作用 |
|---|---|---|
| `bloomThr` | 亮通道 pass：`post.slang` 的 `brightPass()` | **选择器**：哪些像素允许参与光晕 |
| `bloom` 强度 | 合成：`post.slang` 第 133 行 `col = hdr + bloom * post.params.x;` | **增益**：加回去多少 |

降采样与升采样没有任何参数，链长固定 5 级，所以这两个滑杆只改变"选谁"和"加多少"，
不改变开销（bloom 9 个 pass 合计约 0.078 ms，与两参数无关）。

**`bloomThr` 的单位是"白点倍数"**，输入是 tonemap 前的线性 HDR 值：

```slang
float3 brightPass(float3 c, float threshold, float clampPeak) {
    c = min(c, float3(clampPeak));                       // ① 先压掉萤火虫（默认 6.0）
    float br = max(c.r, max(c.g, c.b));                  // ② 取最亮通道
    const float knee = 0.35f;                            // ③ 软膝半宽
    float soft = clamp(br - threshold + knee, 0.0f, 2.0f * knee);
    soft = soft * soft / (4.0f * knee);                  // ④ 膝内二次过渡
    float contribution = max(soft, br - threshold) / max(br, 1e-5f);
    return c * contribution;                             // ⑤ 只保留超出阈值的部分
}
```

`contribution` 在 `br ≤ thr − 0.35` 时为 0、在 `br ≥ thr + 0.35` 时为 1，中间是二次过渡（软膝），
所以不会有硬切边。本场景里真正超过阈值的只有三样东西：**太阳盘（约 16×）**、
**镜面高光（约 8×）**、**接收器发射核心（约 3.6×）**；天空渐变本身就在 1.0 附近。
因此旧默认值 1.0 等于"整片天空都是光源"。`clampPeak = 6.0` 在阈值之前执行，
所以阈值调到 6.0 及以上时亮通道输出为 0，等于关闭 bloom。

`docs/figs/bloom_sources.png`（由 `tools/bloom_sources.py` 生成）把这件事画出来了——
绿色 = 被 bloom 实际点亮的像素：

| bloomThr（强度固定 1.5） | 被点亮的像素 | 占全屏 | 现象 |
|---|---|---|---|
| 1.0 | 180 007 | **19.53%** | 整片天空变绿：天空自己成了光源 |
| **2.5（默认）** | **3 480** | **0.38%** | 只有太阳盘、镜面高光、接收器光斑 |
| 6.0 | 0 | 0% | 全部被 clampPeak 挡住，等于关闭 |

另一种口径（`tools/bloom_probe.py`，强度 1.5）结论一致：阈值 1.0 → 168 579 px（18.29%）被额外
点亮、最大增量 0.325；阈值 2.5 → 1 952 px（0.21%）。

**强度**只作用于已经通过亮通道并被模糊过的那张图，所以它放大的是"亮通道选出来的东西"——
阈值太低时被放大的就是天空本身，这就是"调高 bloom 出现意料之外亮斑"的完整机制。
另外后面还有 ACES 这条 filmic 曲线，强度不是线性可见的：强度加倍不会让光晕亮度加倍。

| 想要的效果 | 设置 |
|---|---|
| 光斑/太阳发光、天空干净 | `bloomThr` 2.5、强度 0.4–0.8（默认 0.55） |
| 现场演示阈值在做什么 | 强度拉到 1.5–2.0，然后在 thr 1.0 ↔ 2.5 之间拖 |
| 完全关闭 | 强度 0（或 thr ≥ 6） |

HUD 面板与右下角光斑图是**合成之后**才画的（`vk_scene.renderOverlays`、`hud.render`），
永远不会被 bloom 糊到——这也是光斑图可以当"测量显示"用的原因。

代码位置：

| 内容 | 位置 |
|---|---|
| 亮通道公式（阈值 + 软膝 + 萤火虫钳制） | `viz/shaders/post.slang` `brightPass()` |
| 四个 pass | 同文件 `fsBloomPre` / `fsBloomDown` / `fsBloomUp` / `fsComposite` |
| 13-tap 降采样、9-tap tent 升采样 | 同文件 `downsample13()` / `upsampleTent()` |

## 2. 收敛参数 `t` 是什么？

`t` 是**螺栓行程的插值系数**，把面板从"零螺栓（理想平板）"连续插值到
"200 次迭代的端到端优化结果"（`data/bolts/North_300m_optimized.txt`）：

```
boltHeight = t × optimizedHeight
```

| t | 面型 | S95 面积 |
|---|---|---|
| 0.00 | 理想平板（零螺栓） | 226.67 m² |
| 1.00 | 端到端优化（36 sun dirs × 200 iter） | 46.26 m² |

`t = 0.5` 不是两张图的混合，而是"螺栓只拧到一半"的真实中间面型：viewer 会用这套螺栓
重新算 TPS + 重力形变，再重新跑整条光追。`F5` 在三档预设之间切换（收敛 / LSQ 椭圆拟合 /
零螺栓），LSQ 档实测 S95 = 47.86 m²。

## 3. 画面上显示的面型是优化前还是优化后的？

默认 `t = 1`，即优化后的面型；按 `F5` 切到 `ZERO`，或把 `t` 拉到 0，即优化前的平板。

两点容易混淆：

- 面型是**算出来的**，不是手工模型。每帧由 `computeBoltSurface` 在 GPU 上重算
  TPS 影响函数叠加 + 20-bin 重力模型，镜面网格通过 SSBO 顶点拉取直接读取
  compute 写出的 `yGrid` / `nGrid`（没有 vertex/index buffer）。
- `F6` 的 1× / 50× / 200× 是**纯显示放大**，只影响法线重建的观感，不参与光追。
  屏幕上的 S95 永远来自真实面型的追踪结果。

## 4. present 模式的区别？三种面型预设分别是什么？

`F10` 循环三种 present 模式（或 `--present fifo|mailbox|immediate`）。它们决定
交换链何时能把画好的图像交给显示器，不影响画面内容：

| 模式 | 行为 | 实测墙钟（59 Hz 面板，关帧率上限） |
|---|---|---|
| `FIFO` | 队列 1 张，必须等显示器取走 → 无撕裂，帧率锁在刷新率 | ≈ 59 FPS |
| `MAILBOX`（默认） | 队列 3 张，新帧替换待显示帧 → 无撕裂，但不锁死提交节奏 | 115 FPS（显示器仍只显示 59） |
| `IMMEDIATE` | 不等 vblank → 可能撕裂，上限只由 GPU 决定 | 841 FPS |

`MAILBOX` 下的"115 FPS"是**提交速率**，不是"显示器看到了 115 帧"。需要确定性的
60 帧节奏时用 `--fps` / `F11`（软件帧率上限），present 模式给不了。

`F5` 的三档面型预设都是真实算出的螺栓行程向量：

| 预设 | 内容 | S95 |
|---|---|---|
| 零螺栓 | 理想平板，未优化基准 | 226.67 m² |
| LSQ 椭圆拟合 | 单参数解析拟合（`North_300m_lsq_init.txt`） | 47.86 m² |
| 端到端优化 | 36 个太阳方向 × 200 次迭代（默认档，也是 `t` 的上端点） | 46.26 m² |

## 5. 原子 A/B 开关是什么？为什么关掉后提高 spp 帧率还是很高？

`3` 开关的是上游研究内核里的**逐光线全局原子操作**（`forward.slang` 无条件执行）：
每个接收器像素的每条光线做一次 `InterlockedAdd(diagBuf[5], 1)`，并对光线有效性位图
（binding 29）做分散的 `InterlockedOr(rayValidity[rayIndex >> 5], 1u << (rayIndex & 31))`。
实时 kernel 把它做成开关，用于单独测量这份开销：

| 配置（1024 spp，4.04 M 光线） | flux 段 GPU | 说明 |
|---|---|---|
| 实时 kernel，原子关 | 0.358 ms | 出厂配置 |
| 实时 kernel，原子开 | **48.79 ms（约 136×）** | 计数器回读证明每帧恰好 `4 044 800` 次原子 |
| 只保留同地址计数器 | +3.5% | 代价几乎全在分散位图的内存流量上 |
| 参照链 `forward.slang`（原子恒开） | 78.0 ms | 上游在"每太阳方向主机同步"的循环里测得 5.2× |

关闭原子时提高 spp 帧率仍高的原因是：flux 段耗时与 spp 成正比，但绝对值很小。
64 spp 为 0.086 ms，1024 spp 为 0.358 ms，而 60 FPS 的帧预算是 16.7 ms。
从 16 spp 提到 1024 spp（光线数 ×64）只增加约 0.28 ms，占预算 1.7%；
限制帧率的不是 GPU（默认是帧率上限，不限速时是约 7.9 ms 的 present 队列）。
打开原子后同一份工作量要 25–49 ms，已经超过 16.7 ms 预算，再提高 spp 就是在超支项上
继续乘系数，于是掉到 20–40 FPS。

## 6. "微调收敛"在调什么？

`[` `]` 与收敛滑杆调的是同一个 `t`，单击步进 0.02，按住按 0.7/s 连续扫。
每一次变化都会重跑物理链：

1. 螺栓高度 → `computeBoltSurface` 用 TPS 影响函数叠加 + 20-bin 重力模型算出
   新的镜面网格 `yGrid` / `nGrid`（compute shader，每帧）；
2. 镜面 mesh 通过 SSBO 顶点拉取读取该网格，形变立刻可见，法线也从网格重算；
3. 同一份法线进入光追：每条光线在镜面上的反射方向变了，落点随之变化，
   光斑形状 / 峰值 / S95 全部重算。

现象是光斑从 226.67 m² 连续收缩到 46.26 m²，峰值从 665 W/px 升到 4808 W/px。

## 7. 每个按键做什么？

每个按键都会在面板显示一行提示（约 3.5 秒）并写入日志，所以"开关生效了但画面变化不明显"
和"按键没生效"可以区分。下面这几条曾经是真 bug：

| 按键 | 作用 | 备注 |
|---|---|---|
| `M` | 热力图量程 自动 ↔ 固定 | 自动档按回读峰值 ×1.25 跟随；固定档把上限钉在当前值。面板显示 `heat auto/FIXED` |
| `8` | 镜场光追 开 / 关 | 关闭时整条 compute 链不记录：flux 段变成 0.000 ms（整帧 GPU 0.34 → 0.240 ms），接收器转冷态，S95 归零，镜场不再绘制。内核文件本身不变 |
| `[` `]` | 微调收敛 `t` | 曾经完全无效：`[` `]` 不是 VK 码（Windows 上是 `VK_OEM_4`/`VK_OEM_6`），旧代码用 ASCII 比较永远不成立 |
| `U` | UI 比例 | 曾经只改了变量、没把比例推给 HUD，所以屏幕上没反应；现在按一次立即重排。面板显示 `ui x…` |
| `F4` | 机位：光束侧视 | 从选中镜方位 +60°、190 m 外侧看入射与反射光束 |
| `F7` | 镜面视图四档 | 面板显示当前档名：`shaded` / `normals` / `slope error` / `height` |
| `F8` | 光束三档 | `off` / `normal` / `strong (2×)`；光束是加性很淡的效果，面板显示当前档 |
| `F9` | 曝光 ×1.25 | `Ctrl+9` 回退 |
| `F11` | 帧率上限 | 60 / 120 / 不限，HUD 首行显示当前值 |

滑块或读数"不动"的同类问题还有一个：`HudStats` 的 `aimOffsetDeg`、`fluxCeil`、`fluxPeak`、
`heatAutoRange` 四个字段在 HUD 里被读取，但在 `viz_main.cpp` 里从未赋值，所以瞄准点滑杆的
数值恒为 0、固定量程显示恒为 auto、光斑图标题的峰值恒为 0。这类"读了但没赋值"的字段可以用

```powershell
python - <<'EOF'
import re
used = set(re.findall(r'st\.([A-Za-z_]\w*)', open('viz/src/hud.cpp', encoding='utf-8').read()))
setv = set(re.findall(r'hs\.([A-Za-z_]\w*)\s*=', open('viz/src/viz_main.cpp', encoding='utf-8').read()))
print('read but never set:', sorted(used - setv))

```

## 8. 螺栓标记为什么有的看不见？S300m 镜的还跑到镜外面？

两个独立原因，都在显示层（物理链路前后都是 CLI 1.951e-07 / 逐像素 0.0）：

**a. 螺栓云与镜面用了两套基准。** 镜面用每镜记录（`helioPosOf` / `helioToWorldDir`），
螺栓用的是引擎的宏观基准（`scene.macroN/U/V`）。引擎在有束靶偏移时会按偏移后的瞄准点
重算法线（定日镜确实要重新指向），而查看器画镜面时忽略了这个偏移，两套基准分叉：

| 镜位 | 束靶偏移 | 两套基准夹角 | 角点越界 | 越界角点数 |
|---|---|---|---|---|
| North / East / South / West | 0° | 0.00–0.03° | 0.00 m | 0/4 |
| South | +60° | **7.91°** | **0.83 m** | **4/4** |
| North | +60° | 0.93° | 0.07 m | 0/4 |

South 退化比 North 严重 8 倍，因为它的宏观法线几乎竖直（nY = 0.990），其基准对瞄准点
极其敏感。修法：螺栓改用与镜面完全相同的每镜基准，并让 `aimPointFor()` 也带上束靶偏移。
修后所有镜位、所有束靶角都是 0 个越界角点 / 0.00 m / ≤0.03°。

**b. `F2` 近景一直是从镜面背面看的。** 相机落在法线负侧约 10 m，不透明镜面把正面的东西
全挡住（螺栓、镀膜高光、镜面反射）。现在近景沿法线正侧取景：
`yaw = azimuth(n) + 22°`、`pitch = elevation(n) + 14°`。

另外两处一并修了：螺栓原来是以节点为中心的八面体，下半截埋在不透明镜面里；
高度原来取最近网格节点，而镜面是双线性插值渲染的（F6 放大到 50×/200× 时会浮起或沉下）。
现在 `tools/bolt_probe.py`（把标记尺寸设为 0 与 0.30 m 各渲一帧，逐像素相减隔离标记像素，
再做连通域计数）实测四个镜位可见 **35 / 35 / 34 / 35** 个标记（South 两个在透视下并成
一个连通域）。

总览机位（`F1`）看不见标记是几何结果：相机与镜面几乎共面（227 m 距离上离镜面平面只有
9.8 m，约 2.5° 掠射），0.44 m 的小方块投影不足一个像素。看标记请用 `F2` 近景，
或加大标记尺寸 `--bolt-scale 0.5`。
