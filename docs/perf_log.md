# docs/perf_log.md — 原始性能数据

> 规则：每次测量追加一行（含命令与口径）。**不要在没测的情况下写"更快了"。**
> 口径说明：`GPU ms` = `vkCmdWriteTimestamp` 的两个时间戳之差（`VK_PIPELINE_STAGE_BOTTOM_OF_PIPE_BIT` 边界）；
> `wall ms` = `std::chrono::steady_clock`（`FrameClock`，QPC）包住整个迭代再取 EMA，含 present 与 OS 合成器时间。
> `FPS` = 1000 / wall ms。
>
> 复现命令（`build\Release` 目录下）：
> ```powershell
> # 数值一致性：viewer 的实时光追 kernel vs 上游基准 NPY（逐像素）
> .\heliostat_viz.exe --frames 40 --spp 1024 --sun 1 --t 0 --dump-flux ..\..\out\flux_parity.npy --log ..\..\out\logs\parity.txt
> # 性能
> .\heliostat_viz.exe --frames 900 --present mailbox --perf-csv ..\..\out\perf.csv --log ..\..\out\logs\perf.txt
> ```

### A/B 开关实测（1024 spp，4.04 M 光线，同进程同场景）

| 配置 | flux 段 GPU ms | wall ms | 相对实时 kernel |
|---|---|---|---|
| 实时 kernel `flux_lite.slang`（cull ON、atomics OFF） | **0.358** | 1.119 | 1.0× |
| cull OFF（`--no-cull`，A1 预裁剪关闭） | 0.351 | 1.235 | 0.98× |
| **atomics ON**（`--atomics`，上游逐光线诊断原子） | **48.789** | 47.612 | **136×** |
| 参照组 `forward.slang`（上游文件原样，原子恒开） | **78.000** | 84.211 | **218×** |
| 64 spp + atomics ON | 2.784 | 3.598 | 32×（对比 64 spp 的 0.086 ms） |

**原子开关是真的**：`diagBuf[5]`（binding 31，上游诊断计数器）被 viewer 直接读回验证：
200 帧 × 3 950 像素 × 1 024 spp = **808 960 000**，与实测读数完全一致；关掉开关时该计数器保持 0。

**为什么是 136× 而不是 BASELINE 里的 5.2×**：上游那次 5.2× 是在"每个太阳方向 6–7 次主机
全同步"的循环里测的，原子的**延迟**被暴露在关键路径上；本包每帧只提交一次、2 帧飞行，
同样的原子流量只付它在 GPU 上的实际代价。两个数字都如实记录：

* 同地址原子（`InterlockedAdd(diagBuf[5])`）单独存在时只有 **+3.5%** —— 硬件能把同一 warp 内
  同地址的原子合并成一次操作；
* 真正贵的是 `InterlockedOr(rayValidity[rayIndex>>5], …)`：地址逐光线分散，无法合并，
  每次都是对 1 MB 位图的读改写。

## 修复轮（2026-08：用户反馈"UI 镜像 / 画面自动切换后自动关闭"之后的主程序打磨）

修的都是**主程序功能缺陷**（不是画面调优），每条都给出证据：

| # | 现象 | 根因 | 证据 / 复现 |
|---|---|---|---|
| 1 | HUD 整体上下镜像（文字倒置、面板跑到底部） | `vsHud` 沿用了 scene 通道的 NDC 约定。scene 渲染进 HDR 时 NDC 是 y-up，由 composite 翻转后上屏；HUD 直接画到 swapchain，必须显式 `ndc.y = y/H*2-1`（Vulkan 帧缓冲原点在左上、y 向下） | 修前：绿色标题在 rows 628..683（画面底部）；修后 rows 31..78，且 ASCII 预览可读出 "HELIOSTAT STUDIO" |
| 2 | **接收器热力图完全没显示**（最重要的画面功能） | UBO 打包错位一格：`pixelHeight` 写到 float 76，而 shader 读的 `ground.w` 是 float 75。接收器只画了 **12 行**（应 50 行），采样到 flux 纹理顶部 12 行，而光斑在 22–28 行 | 修前热力图色像素 2 285；修后 53 682。并且随收敛滑杆变化：t=0 亮区 240 px 高，t=1 聚焦后 106 px |
| 3 | **收敛滑杆 / F5 面型预设无效**（S95 一直是平板值） | 预置螺栓文件按 `data_proxy/../bolts` 找，实际在 `data/bolts/`；加载失败后静默退化成零螺栓 | 修前 `--t 1` 仍报 S95 226.67 m²；修后 46.26 m²、peak 4808.1（与 CLI `--bolts` 完全一致） |
| 4 | 面板滑块拖不动（点击命中失败） | `WM_LBUTTONDOWN` 只更新按键状态、不更新指针位置；真实鼠标会先产生 WM_MOUSEMOVE 所以看不出来，合成点击必失败 | 日志：`[hud] press at (351,367) -> slider -1 (no hit)`——应用拿到的是真实光标位置而不是发布的坐标 |

### 1. 右下角光斑图（`F` 开关，`--no-flux-map` 默认关）

屏幕右下 176×72 的内嵌通道，把接收器 157×50 的 flux 纹理直接画成热力图，外框 + S95
等值线（`scene.stats.x` = GPU 二分出的 `findLevel` 结果），右上角标注 `S95 46.3 m2 / peak 4808 W`。
复用**同一次回读**（每 15 帧一次的 `FluxReadback`），因此开关本身 0 额外 GPU 成本：
`fsFluxMap` 是一个全屏三角形之外的独立小 pass，实测帧时不变（0.485 ms，见下表）。

### 5. Bloom 阈值：为什么"调高之后出现意料之外的亮斑"

`docs/figs/bloom_threshold.png`（由 `tools/make_bloom_fig.py` 生成，逐像素对比"关 bloom 基准"）：

| 亮度阈值 | 被 bloom 额外点亮的像素（>0.05） | 占全屏 | 强光晕像素（>0.15） | 最大增量 |
|---|---|---|---|---|
| 1.0（**旧硬编码默认**） | **168 579** | **18.29%** | 9 668 | 0.325 |
| 2.5（新默认） | 1 952 | 0.21% | 498 | 0.307 |
| 6.0 | 0 | 0% | 0 | 0.008 |

结论：threshold = 1.0 时**整片天空渐变都在亮通道之上**，5 级 tent 升采样把它摊成大片光晕；
调到 2.5 后只剩真正 HDR 的发射体（太阳盘 ≈16×、镜面高光 ≈8×、接收器核心 ≈3.6×），
光晕像素减少 **85×**。另加 `bloomClamp = 6.0` 萤火虫钳制，防止单个超高像素种出一圈亮斑。
面板新增 `bloom thr` 滑杆（0.5–8.0），CLI 新增 `--bloom-thr` / `--bloom`。

## 打磨轮 2（HUD 清晰度 / 光斑图居中 / 面板瘦身 / 机位跟随选中镜 / 帧率上限）

### 1. 罗盘与标识字符：为什么"模糊"和"脏"

三处真实原因，全部是绘制层的问题（与 GPU、字体渲染无关）：

| 症状 | 根因 | 修法 |
|---|---|---|
| 面板分割线、罗盘刻度、光斑图边框"发虚/发脏" | `rect()` 直接乘 `m_scale` 后不做取整：边界落在半像素上时每个边缘都与背景混合一次 | `rect()` 把所有坐标/尺寸 `floor(x+0.5)` 到整数设备像素（`w,h` 至少 1 px） |
| 字母"模糊不清"（`--hud-scale` 不是整数时尤其明显） | 字体图集用 **NEAREST** 采样，而字形块尺寸是 `5*scale`（例如 1.3×1.7 倍时为 8.5/11.9 px）→ 有的源列被拉成 1 px、有的 2 px，笔画粗细不均 | `text()` 改为**整数倍字形块**：`glyphW/H` 与步进都取整，任何缩放都是干净的像素放大 |
| 罗盘指针/太阳标记/刻度出现"脏图案" | ① 15° 刻度用 1 px 斜线 `line()` 画，斜线在无 MSAA 下产生断续的半亮像素；② 太阳菱形由**四条半透明斜线**叠成，交叠处被混合两次；③ 指针是 0.9 alpha 斜线再叠一个方块 | ① 刻度改成环上的**轴对齐小方块**（12 个/30°）；② 菱形改成共享中心顶点的**四个不透明三角形**；③ 指针改成**单个不透明填充三角形** + 方块轴心；④ 罗盘整体整数对齐；⑤ 删掉已经没有人用的 `line()` 原语（现在只有两种原语：像素对齐矩形 + 位图文字） |
| 直接画在场景上的标签（罗盘字母、光斑图标题）边缘不清、蓝字压在蓝天上 | 5×7 字体在天空背景上没有对比度 | 罗盘四个方位字母改为 **2 倍字号（10×14 px）+ 12×16 深色底片**（实测每个底片内 60–75 个字形像素）；光斑图标题加半透明底板 + 1 px 投影（新增 `textShadow()`） |

### 2. 光斑图无论哪个镜都居中（轴对齐 + 圆柱卷绕）

接收器光斑图是**圆柱展开**：u（157 列）绕一圈是周期量，v（50 行）是高度。
`tools/inset_probe.py` 用"关 bloom/关 UI 差异"以外的方法直接量——把 `--no-ui` 的反例
（`--no-inset-centre`，即旧的原始贴图）与新实现逐帧对比，统计内嵌矩形内光斑的
加权质心偏移、峰值像素偏移与**水平展布**（分裂的光斑是双峰分布，展布会爆炸）：

| 镜位 | 旧（原始贴图）质心偏移 | 旧 峰值偏移 | 旧 水平展布 | 新 质心偏移 | 新 峰值偏移 | 新 水平展布 |
|---|---|---|---|---|---|---|
| North | −11.0 px | **−177.0 px** | **72.8 texel** | −0.9 px | −4.0 px | 8.9 texel |
| East | −86.9 px | −88.0 px | 10.0 | −0.8 px | 0.0 px | 8.9 |
| South | 0.0 px | +1.0 px | 12.0 | −0.8 px | −1.0 px | 12.0 |
| West | +87.0 px | +87.0 px | 11.4 | −0.9 px | −3.0 px | 9.0 |

（内嵌矩形 358×114 px；**PASS** 判据：质心 |偏移| ≤ 6 px 且水平展布 ≤ 25 texel。）

关键发现：North 镜的光斑质心 u = **0.003**——它正好骑在 u = 0 的接缝上，所以旧实现里
**一半画在最左边、一半画在最右边**（峰值偏移 −177 px、展布 72.8 texel），也就是用户说的
"被切开"；而它的**质心**看着是居中的（两半对称），所以只靠质心判断会漏掉这个 bug。
East/South/West 的质心分别是 0.254 / 0.502 / 0.751，正好相差 1/4 圈。

修法：CPU 端在回读时算**圆形质心**（对 (cos 2πu, sin 2πu) 做通量加权平均，u 是周期量；
v 直接加权平均），放进 UBO 新的 `fluxCenter`；片元里把 u 卷绕到质心：
`uv.x = frac(uvIn.x - 0.5 + centre.x)`。四个镜位现在都在 **2.5 px / 12 texel** 以内居中。

### 5. 60 / 120 FPS 帧率上限（默认 60）

present 模式本身表达不了"60 FPS"：`MAILBOX` 跟着显示器刷新走（本机 59 Hz 面板实测 115 FPS），
`IMMEDIATE` 则全速跑。所以在帧循环里加了**软件帧率上限**：用单调时钟排程，剩余时间用
**高精度可等待定时器**（`CreateWaitableTimerExW` + `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`，
kernel32，不引入任何新库、不调用全局 `timeBeginPeriod`）粗睡 + 自旋收尾。
放在帧首，所以 HUD 里的 `wall ms` 就是被限速后的帧时间；GPU 时间戳不受影响。

| 配置 | 墙钟 | 帧率 |
|---|---|---|
| 默认（cap 60，MAILBOX） | 16.687 ms | **59.9 FPS** |
| `--fps 120` | 8.349 ms | **119.8 FPS** |
| `--fps 0`（MAILBOX） | 7.885 ms | 126.8 FPS（此时受 present 队列限制） |
| `--fps 0 --present immediate`（性能口径） | 1.189 ms | 841 FPS |

## 打磨轮 3（"有些螺栓点不在镜面上 / S300m 的螺栓跑到镜外"）

用户报告的两个现象**都是显示层的 bug，物理链路一直是对的**（parity 未变：CLI 1.951e-07、
viewer 逐像素 0.0）。但它们是**两个独立的原因**，一个叠加一个：

### 原因 1：螺栓云与镜面用了**两套不同的基准**

| | 镜面（mode 3） | 螺栓（旧 mode 4） |
|---|---|---|
| 位置 | `helioPosOf(hi)`（每镜记录） | `scene.helioPos`（引擎的"当前镜"） |
| 方向 | `helioToWorldDir(hi, …)`（查看器算的每镜基准） | `toWorldDir(…)` = `scene.macroN/U/V`（**引擎**基准，**含束靶偏移**） |

引擎的 `updateAim()` 会按**束靶滑杆**的偏移重新计算宏观法线（物理上定日镜确实要重新指向），
而查看器画镜面用的 `macroBasisFor()` **忽略了这个偏移** → 两套基准分叉。实测（新增的
`boltFit` 诊断，随 `--state-log` 输出 `boltsOut / worst / frame / nrm`）：

| 镜位 | 束靶 | 两套基准夹角 | 角上螺栓越界米数 | 越界角点数 |
|---|---|---|---|---|
| North | 0° | 0.03° | 0.00 m | 0/4 |
| East | 0° | 0.00° | 0.00 m | 0/4 |
| South | 0° | 0.02° | 0.00 m | 0/4 |
| West | 0° | 0.02° | 0.00 m | 0/4 |
| **South** | **+60°** | **7.91°** | **0.83 m** | **4/4** |
| **South** | **−60°** | 6.76° | 0.72 m | 4/4 |
| North | +60° | 0.93° | 0.07 m | 0/4 |

注意 South 的退化比 North 严重 **8 倍**：它的宏观法线几乎竖直（nY = 0.990），镜面基准
"绕法线转多少"对瞄准点极其敏感——这正是用户单独点出 S300m 的原因。

修法：① 螺栓改用与镜面**完全相同**的每镜基准（`pc.extra` 传选中镜下标）；
② `aimPointFor()` 补上束靶偏移，让**画出来的镜面**与**被追踪的镜面**也一致（之前束靶≠0 时
画出来的镜面倾斜最多偏 1.2°）。修后上表所有情况都是 `boltsOut 0 / worst 0.00 m / frame ≤0.03°`。

### 原因 2：F2 近景一直是从镜面**背面**看的

`applyPreset(1)` 用固定 yaw = bearing + 16° 取景，对北镜就是 196°——相机落在镜面法线的
**负侧**（实测 `dot(camera − plate, n) = −10.0 m`）。镜面是不透明的，于是**长在正面的东西
全被自己挡住**：螺栓标记、玻璃镀膜高光、镜面反射。用户看到的"有些螺栓点不显示在镜面上"
就是这个。修法：`applyPreset()` 接收镜面法线，近景改为沿 **+n 方向**取景
（`yaw = azimuth(n) + 22°`、`pitch = elevation(n) + 14°`）。

另外两处显示层的粗糙点一并修掉：
* 螺栓标记原来是**以节点为中心**的八面体 → 下半截埋在（不透明的）镜面里，只露出半个；

### 1. 太阳轨迹改为德令哈的真实日轨（夏至日）

场地按**中国青海德令哈**（50 MW 熔盐塔式电站所在地）取：**37.37°N / 97.37°E**。
轨迹不再是"三个纬度 + 赤纬 0"的示意，而是**该场地指定日期的真实日轨**：

$$\cos H_0=-\tan\varphi\cdot\tan\delta,\qquad h_{noon}=90^\circ-|\varphi-\delta|,\qquad
\text{昼长}=\frac{2H_0}{15}\,\text{h}$$

| 档（`9` 循环） | 日期 | 赤纬 δ | 正午高度角 | 昼长 | 日出/日落（真太阳时） | 日出/日落（北京时间） |
|---|---|---|---|---|---|---|
| **1 夏至（默认档）** | 6 月 21 日 | **+23.44°** | **76.07°** | **14.58 h** | 04:59 / 19:01 | 06:29 / 20:32 |
| 2 春/秋分 | 3 月 21 / 9 月 23 | 0° | 52.63° | 12.00 h | 06:00 / 18:00 | 07:31 / 19:31 |
| 3 冬至 | 12 月 21 日 | −23.44° | 29.19° | 9.42 h | 07:17 / 16:43 | 08:48 / 18:14 |

实测（`--sunpath n --sun-hour H`，读 `[state]` 的 `az/el/lst/bjt/daylen/noonel`）：

要点：
* 方位角沿用本场景约定（`az = atan2(x, z)`，**0° = 正南**，+X 为东），所以正午 az = 0 ✓。

  北京时间 = 真太阳时 + 1h31m），并把日期、赤纬、正午高度角、昼长一起列出来。
* 该轨迹驱动的太阳方向与滑杆走**完全同一条物理链**（`setSun` → 光追），不是"演示模式"。
* 新增 `--sun-hour <deg>`：把时角钉住并暂停动画（可复现的静帧/测试用）。

## 打磨轮 5（按键可发现性 / 面板自适应 / UI 放大）

用户逐条追问了按键的作用（`M`/`8`/`[`/`]`/`F4`/`F7`/`F8`），其中有 **两个是真 bug**，
其余是"功能生效了但界面没有任何反馈"。逐条结论与修法：

| # | 问题 | 结论 | 修法 |
|---|---|---|---|
| 1 | `M` 是什么？为什么没反应？ | 功能是**热力图量程 自动 / 固定**；它生效了，但当自动量程当前值≈固定值时**画面几乎不变**，面板只有一处 `(auto/fixed)` 小字，所以看不出按键生效 | 面板状态行改成 `heat AUTO/FIXED<=5940`，并在按下时给出 toast：`M -> heat range: FIXED (ceiling 5940 W/px)` |
| 2 | `8` 关闭镜场光追为什么没反应？ | **真 bug**：`8` 实际上绑的是"关闭太阳日轨"（`ui.sunPath = 0`），而帮助文字写的是"8 field off"——功能根本没实现 | `8` 改为**真正关闭镜场光追**：跳过整条 compute 链（deform→flux→finalize→S95），镜场不再绘制、接收器转为冷态、S95/峰值读数归零。实测（按 `8` 后的退出报告）：`deform 0.000 | flux 0.000 | scene 0.064 | ... | total 0.240 ms`（对比默认 ~0.34 ms 且 flux 非零） |
| 3 | 日轨演示时面板容纳不下、太阳时/高度出框 | 面板高度原先由**公式**估算，日轨多两行就会溢出 | 面板底板改为**按实际绘制内容测量**（先把内容画进顶点表、再按测得高度插入底板）；若内容仍高于窗口，`build()` 会**自动缩小 UI 比例**重排（最多 10 次，下限 0.6）。实测 1280×720 + `--hud-scale 3.0`：自动落到 **1.84**（367 HUD 单位 × 1.84 = 675 px < 720）✓ 1280×720 + `--hud-scale 2.0` → **1.70** ✓ |
| 3b | 希望进一步放大 UI 与字体 | — | 新增**自动 UI 比例**（默认）：`scale = clamp(round(min(W/1280,H/720)), 1..3)`，实测 1280×720→**1.00**、**1920×1080→2.00**（最大化到笔记本主屏就是 2 倍，字形 10×14 px）、2560×1440→2.00、1366×768→1.00；按键 **`U`** 循环 AUTO→1→1.5→2→2.5→3，`--hud-scale` 仍可钉死；面板与状态行显示当前比例 |
| 4 | `[` `]` 没反应 | **真 bug**：`[`/`]` 不是 VK 码（Windows 上是 `VK_OEM_4` = 0xDB / `VK_OEM_6` = 0xDD），原代码用 ASCII 0x5B/0x5D 比较，**永远不成立** | 改用 `VK_OEM_4/VK_OEM_6`；单击步进 t ±0.02（一按就有变化），按住按 0.7/s 连续扫，并给出 toast `] -> convergence t = 0.490 (S95 54.91 m2)`。实测：`[` 长按 t 1.000→0.478、`]` 长按回到 1.000 |
| 5 | `F4` 是什么？ | 机位预设 **光束侧视**（离镜面 190 m、沿选中镜方位 +60° 侧看入射/反射光束） | 面板增加 `camera: beam side` 一行（`camera.presetName()`），按键时 toast `F4 -> camera: beam side view (mirror to tower)` |
| 7 | `F7` 需要说明是哪一类图 | 面板原来只显示 `view 2` 这种数字 | 面板改为 `view normals (F7)`（四档：`shaded / normals / slope error / height`），按键时 toast 同步说明 |

### 打磨轮 5 的补丁（面板"变大且空白"——我自己引入的回归）

用户反馈"左上面板太大，且其中不显示任何内容了"。**两个都是我在上一轮改面板时引入的**：

1. **面板空白（严重）**：我把面板底板改成"先画内容、再按实测高度插入底板"，实现时写成
   `m_cpu.resize(bgStart)` → 拷贝底板 → `m_cpu.resize(keep)` → `insert(...)`：
   `resize(keep)` 把被截断的**内容顶点重新填成全零**（值初始化），于是整块内容消失，只剩底板。
   修法：先把内容拷进临时 vector，再 `resize(bgStart)` 画底板，最后把内容**追加**回去。
2. **面板太大**：① 自动 UI 比例在 1080p 直接取 2×（面板 884×680 px ≈ 屏幕 29%）；② 面板宽度按
   `hudW*0.62` 估算且**不按文字实测**，同时状态行有 100 字符的超长行会把面板撑宽/溢出。

修法与实测（新增 `tools/panel_probe.py`：开/关 UI 两帧逐像素相减 → 面板包围盒 + 盒内"非底板"
像素占比；`--no-beams --no-cards --sun-hour 0` 保证两帧只有 HUD 差异）：

| 窗口 | 自动 UI 比例 | 面板盒（像素） | 占屏 | 盒内内容像素占比 |
|---|---|---|---|---|
| 1280×720 | 1.00 | 486×340 | **17.9%** | 26.0% |
| 1280×720（日轨开启） | 1.00 | 486×355 | 18.7% | 41.5% |
| **1920×1080** | **1.50** | 729×511 | **18.0%** | 28.3% |
| 2560×1440 | 2.00 | 972×680 | 18.2% | 29.1% |

- **自动比例档位改为 1 / 1.5 / 2 / 3**（`fit = min(W/1280, H/720)`：≥1.4→1.5、≥1.9→2、≥2.8→3），
  所以 1080p 是 **1.5×**（字形 8×11 px，仍然清晰）而不是 2×，面板占屏从 29% 降到 **18%**；
  `U` 仍可循环、`--hud-scale` 仍可钉死、`H` 一键隐藏。
- 面板盒现在**两个方向都按实测内容**拟合（宽 = 最宽一行 + 边距；高 = 内容高度），
  状态行压到 ≤65 字符，去掉了一处误留的 `file %s` 空占位；装不下时依旧自动缩小比例重排。
- 修后 `panel_probe.py` 在四种窗口下都报 `PASS`（盒内内容占比 26–42%，此前是 **0%**）。
